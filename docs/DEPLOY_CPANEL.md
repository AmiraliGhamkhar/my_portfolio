# cPanel deployment guide

This release is a static Vite build plus a same-origin PHP API. Node.js is required on the build machine only; do not configure a production Node application for the public site.

## 1. Confirm the hosting requirements

- PHP **8.2 or newer** for both the web handler and CLI, with `PDO`, `pdo_mysql`, `fileinfo`, `session`, and `json` enabled. `mbstring` is recommended; the API has a UTF-8 length-check fallback when it is absent.
- MySQL 8+ or a compatible, current MariaDB release with InnoDB, JSON functions, and `CHECK` constraints.
- Apache with `mod_rewrite`, `mod_headers`, `mod_deflate`, and `mod_expires`, and permission to use the supplied `.htaccess` files.
- HTTPS enabled for the site before signing in to the CMS.
- A cPanel database and database user. Use a dedicated user; runtime needs `SELECT`, `INSERT`, `UPDATE`, and `DELETE`, while migrations additionally need `CREATE`, `ALTER`, `INDEX`, and `REFERENCES` for schema constraints.

Check the cPanel-selected PHP version rather than assuming the system `php` command uses the same one as the website. On hosts that provide versioned binaries, use the PHP 8.2 CLI binary (often `ea-php82`) for the commands below.

## 2. Build and verify locally

From the repository root:

```bash
npm ci
npm run typecheck
npm test
npm run build
```

The build writes the finished static site and API entrypoint to `dist/`. Upload the **contents** of `dist/` to the domain's document root (usually `public_html`), not the `dist` directory itself. Preserve hidden files, especially `.htaccess`, and keep the `api/` and `uploads/` directories in place. `sitemap.xml`, locale routes, project routes, fonts, and hashed assets are generated by the build.

The production frontend calls only same-origin `/api/v1/...` URLs. It does not call `localhost` and does not need a Node server.

## 3. Install the private PHP application

Keep PHP source, configuration, logs, rate-limit data, and database credentials **outside** the web document root. With the default cPanel layout, the public entrypoint at `public_html/api/index.php` looks for:

```text
~/portfolio-private/bootstrap.php
~/portfolio-private/src/router.php
```

Copy the contents of the repository's `backend/` directory into `~/portfolio-private/`, preserving its `bin/`, `migrations/`, `seeds/`, and `src/` subdirectories. Do not upload `backend/` under `public_html`.

Copy `config.example.php` to `config.php` in that private directory. Set the database host, database name, database user, and password to the values created in cPanel. Also set a unique, unpredictable `app_key` of at least 32 characters; generate one with:

```bash
php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
```

Some cPanel PHP handlers support environment variables; others do not. The example reads `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `PORTFOLIO_APP_KEY`, and related settings from the environment. If the host does not provide them, edit **only the private `config.php`** to supply the values there. Never put real credentials in this repository or in `public_html`. Restrict the file to the account/PHP user (for example, mode `0600` where supported).

Review these paths in the private configuration:

- `data_dir`: writable private storage for rate-limit records and API logs. The example places it next to `portfolio-private/`, outside the document root.
- `upload_dir`: writable storage for uploaded images. The default assumes `~/public_html/uploads`; change it if this domain uses a different document root.
- `upload_url`: normally `/uploads`.
- `allowed_origin`: the exact HTTPS origin, with no path, such as `https://amiralighamkhar.ir`.
- `trust_proxy_https`: leave false for direct Apache HTTPS. Enable only if the host terminates TLS at a trusted proxy and documents a trustworthy `X-Forwarded-Proto` header.

The entrypoint also supports `PORTFOLIO_PRIVATE_DIR` if the private directory is elsewhere. If the public origin/domain changes, update the configured origin and matching canonical-origin values in `public/.htaccess`, `public/robots.txt`, `index.html`, `src/lib/seo.ts`, and the origin assertions in `scripts/check-build.mjs`, then build again.

## 4. Create the public upload directory

Create `public_html/uploads` (or the configured equivalent) and copy in the supplied `dist/uploads/.htaccess`. The PHP user must be able to create files there, but the directory must not be executable. Use the narrowest ownership/permissions your host supports; do **not** use `777`. The upload rules disable directory listing and deny execution of PHP and other script extensions.

`public/api/.user.ini` sets conservative upload and error-display limits on hosts that honor per-directory PHP settings. If cPanel overrides these values, configure equivalent limits in its PHP INI editor. The API accepts JPEG, PNG, WebP, and AVIF images up to 6 MB, verified by file MIME detection; SVG and arbitrary documents are not accepted.

## 5. Run migrations, seed content, and create the first admin

Open a cPanel shell/SSH session and use the PHP 8.2 CLI binary:

```bash
cd ~/portfolio-private
php -v
php bin/migrate.php
php bin/seed.php
php bin/create-admin.php --email=owner@example.com --name='Portfolio owner'
```

Replace the email with the real administrator's address. The password is entered interactively and is not placed in shell history. `seed.php` is idempotent and uses `INSERT IGNORE`; it does not overwrite edited rows. Run it before creating the admin or signing in. Do not create an admin by inserting a plain-text password into MySQL.

If the application is stored outside the default path, make sure the API entrypoint's `PORTFOLIO_PRIVATE_DIR` points to it. Verify that the PHP web user can write to the configured private `data_dir` and `upload_dir`, without granting broader access than necessary.

## 6. Smoke-test the site and API

Open these URLs over HTTPS:

- `/fa/` and `/en/`: each should render the correct language and direction.
- `/fa/projects/`, `/en/projects/`, both contact pages, and all seeded project details: direct deep links must load, not only links reached from the homepage.
- `/admin/`: the page should show the sign-in screen; the API must be configured before login can succeed.
- `/api/v1/health`: after database configuration, expect HTTP 200 and a JSON envelope containing `data.status = "ok"`.
- `/sitemap.xml`: it should list the localized static routes.

Sign in and verify that an unauthenticated admin request returns 401, a valid CMS edit persists after refresh, the Persian and English translation tabs do not overwrite one another, a contact submission appears in Messages, and an uploaded image can be selected in the profile or a project. Test that an invalid file type and an image over the size limit are rejected. Check the Apache/PHP error log if any of these fail; API responses intentionally do not expose stack traces.

The contact form stores submissions in the CMS. This implementation does **not** send notification email; configure a separate mail workflow only if one is desired.

## 7. Updates, backups, and rollback

1. Back up the current document root, the private application/configuration, the uploads directory, and the database.
2. Run the local typecheck, tests, and build again.
3. Upload the new `dist/` contents, including hidden `.htaccess` files. Avoid deleting `uploads/`.
4. Update the private PHP files as needed, but preserve `config.php`, private data, logs, and uploaded files.
5. Apply new versioned migrations with `php bin/migrate.php`; re-running already applied migrations is safe. Run `php bin/seed.php` only when you intend to add missing seed rows.
6. Repeat the smoke tests above.

For rollback, restore the previous static build and private PHP code from backup. Database migrations are forward-only in this starter; take a database backup before schema changes and restore it only when necessary. No production deployment or cPanel behavior has been verified from this development workspace.
